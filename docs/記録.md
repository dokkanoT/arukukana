# 判断の記録

設計で決めたことを「決めたこと／理由／ほかの案」で残す。新しい判断は下に足していく。

## 一日目 土台（2026-11-10）

### 1. 暗号は Web Crypto API だけで組む

- **決めたこと**：暗号ライブラリを入れず、ブラウザ標準の `crypto.subtle` だけを使う。
- **理由**：標準アルゴリズムの組み合わせだけなので、処理を 1 行ずつ説明できる。秘密鍵を「取り出せない鍵」として持てるのは Web Crypto ならでは。
- **ほかの案**：libsodium などのライブラリ。便利だが、鍵がただのバイト列になり、JavaScript から読めてしまう。

### 2. ハイブリッド暗号にする（本文は AES-GCM、鍵の受け渡しは ECDH）

- **決めたこと**：手紙ごとにランダムな内容鍵 K（AES-GCM 256bit）で本文を暗号化し、K を読める人ごとに包んで一緒に保存する。
- **理由**：本文の暗号文は 1 つのまま、あて先と差出人の両方が開けられる。AES-GCM は改ざんも検知できる。
- **ほかの案**：あて先の公開鍵から作った鍵で本文を直接暗号化する。差出人が自分の送った手紙を読み返せなくなる。

### 3. K を包むたびに使い捨ての鍵ペアを作る（ECIES と同じ形）

- **決めたこと**：K を包むときは毎回、使い捨ての ECDH 鍵ペアを作り、相手の公開鍵との共有秘密を HKDF-SHA256 に通して「鍵を包む鍵 KEK」にする。使い捨ての公開鍵（epk）だけを手紙に添える。
- **理由**：同じ相手に何通送っても、包んだ鍵は毎回別物になる。差出人の端末の秘密鍵を暗号化に使わないので、封をする処理が相手の公開鍵だけで完結する。
- **ほかの案**：差出人とあて先の端末の鍵どうしで ECDH する。2 人の間の共有秘密がいつも同じになり、1 つ漏れたときの影響が大きい。

### 4. HKDF の info に手紙の ID と uid を入れる

- **決めたこと**：info は `arukukana-v1|{capsuleId}|{uid}`。salt は毎回ランダムな 16 バイト。
- **理由**：別の手紙・別の人あての KEK と必ず別物になる。包んだ鍵を別の手紙や別の uid に付け替えても開かない。先頭の `v1` は、あとで方式を変えたときに古い手紙と区別するため。
- **ほかの案**：info を空にする。動くが、鍵の使い道が結びつかない。

### 5. AAD でメタデータと暗号文を結びつける

- **決めたこと**：AAD は `capsuleId|to|from|header`（body は末尾が `body`）。
- **理由**：`to` と `from` は平文で保存するので、書き換えられたら復号が失敗するようにする。末尾の区別は、header と body を同じ K で暗号化しているため。これがないと、サーバー側で 2 つの暗号文を入れ替えても復号が通ってしまう。
- **ほかの案**：当初の仕様は `capsuleId|to|from` だけだった。入れ替えで文面が漏れることはないが、表示を壊せるので区別を足した。

### 6. 秘密鍵は extractable=false のまま持つ

- **決めたこと**：端末の秘密鍵は `extractable: false` で作る。取り出した内容鍵 K も `unwrapKey` で「取り出せない鍵」として受け取る。
- **理由**：万一ページに悪意あるスクリプトが入っても、鍵の中身そのものは読み出せない。
- **ほかの案**：鍵をバイト列で持つ。機種変更時の引き継ぎは作りやすいが、漏れやすい。
- **正直に書くこと**：K は封をする瞬間だけ、包むために取り出し可能にしている。

### 7. 鍵の合言葉は、ひらがな 4 語

- **決めたこと**：`SHA-256(公開鍵)` の先頭 4 バイトを、256 語のひらがな単語リストで 4 語にする。
- **理由**：1 バイトがちょうど 1 語になる。16 進数の羅列より、声に出して読み合わせやすい。濁点だけが違う語（かき／かぎ）は聞き間違えるので入れていない。
- **ほかの案**：16 進数や絵文字。絵文字は機種で見た目が変わり、声で伝えにくい。
- **正直に書くこと**：4 バイト（約 43 億通り）は、うっかりの取り違えに気づくための長さ。本気で似た合言葉を作ろうとする相手を防ぐ長さではない。

### 8. 場所・日時の制限は端末側の判定

- **決めたこと**：`openBody` は鍵があれば復号できる。「着いたか」「開けられる日を過ぎたか」は画面側が先に確かめる。到着の条件は `距離 ≤ 半径 + min(GPS精度, 30m)`。
- **理由**：GPS には誤差があるので、精度ぶんだけ甘くする。ただし精度が悪いほど遠くから開けられてしまうので、上乗せは 30m まで。
- **ほかの案**：場所から鍵を導出する方式（その場所に行かないと鍵が作れない）。今後の展望。

### 9. 距離はハーバサイン式で自前計算

- **決めたこと**：`geo.ts` に 10 行ほどで書く。
- **理由**：数十メートルの判定には、地球を球とみなす近似で十分。ライブラリを足すほどの量ではない。
- **ほかの案**：turf.js などの地理ライブラリ。

### 10. 匿名認証で、登録画面を作らない

- **決めたこと**：起動時に Firebase の匿名認証で自動サインインし、終わってから画面を出す（`AuthGate`）。
- **理由**：審査員がログインなしで使える。uid があるので、セキュリティルールで「自分あての手紙だけ読める」を書ける。
- **ほかの案**：認証なし。だれでも全部の手紙（暗号文）を読み書きできてしまう。
- **正直に書くこと**：匿名ユーザーはブラウザのデータを消すと別人になる。秘密鍵も同じ端末にしかないので、機種変更で手紙は引き継げない。

### 11. フロントは Vite + React + TypeScript（strict）、スタイルは Tailwind CSS v4

- **決めたこと**：SPA として作り、ルーティングは react-router。デザイントークンは `index.css` の `@theme` に書く。
- **理由**：`@theme` に書いた色は CSS 変数になり、同時に Tailwind のクラスとしても使える。設定が CSS 1 ファイルにまとまる。
- **ほかの案**：Next.js。サーバー側の処理が要らない作品なので、仕組みが少ない SPA にした。

### 12. テストは Vitest、環境は Node

- **決めたこと**：暗号・距離計算・単語リストをテストする。ブラウザを模した環境（jsdom）は入れない。
- **理由**：対象は純粋なロジックで、Node にも Web Crypto がある。
- **正直に書くこと**：実ブラウザ（特に iPhone の Safari）での暗号の動作は、画面ができてから実機で確かめる。

## 二日目 コア部分（2026-11-11）

### 13. AAD に「header か body か」も入れる

- **決めたこと**：AAD を `capsuleId|to|from|header` と `capsuleId|to|from|body` に分ける（仕様書の `capsuleId|to|from` に 1 語足した）。
- **理由**：同じ鍵 K で header と body を暗号化しているので、足さないと 2 つの暗号文を入れ替えても復号が通ってしまう。入れ替えると開けないことをテストで確かめている。
- **ほかの案**：header 用と body 用に別の鍵を作る。包む鍵が倍になり、保存する量も増える。

### 14. Firestore は通常版の SDK を使い、届いた手紙は見張る（onSnapshot）

- **決めたこと**：`firebase/firestore` で、自分あての手紙を `where('to','==',uid)` で見張る。
- **理由**：友だちが埋めた手紙が、開きなおさなくても地図に出る。
- **ほかの案**：軽量版（`firestore/lite`）。バンドルは小さくなるが、見張る機能がない。

### 15. 手紙の ID を先に決めてから封をする

- **決めたこと**：`doc(collection(...))` で ID だけ先に作り、その ID を AAD と HKDF の info に入れて封をしてから保存する。
- **理由**：ID を暗号文に結びつけるには、暗号化の前に ID が要る。
- **ほかの案**：`addDoc` で保存時に ID をもらう。ID を暗号文に結びつけられない。

### 16. ルールで、保存する値の長さまで決める

- **決めたこと**：公開鍵 87 文字、IV 16 文字、salt 22 文字、包んだ鍵 64 文字、暗号文は合計 16KB まで。あて先が実在すること（`exists`）も見る。手紙の書き換えは不可。
- **理由**：サーバーは中身を読めないので、せめて形で縛る。大きなデータの置き場にされるのも防ぐ。長さはテスト（「保存する値の長さ」）で固定している。
- **ほかの案**：フィールド名だけ確かめる。任意の長さの文字列を置けてしまう。

### 17. 地図は MapLibre GL JS + OpenFreeMap、色だけ夜トーンに上書き

- **決めたこと**：OpenFreeMap の dark スタイルを読み込み、色を自分のトークンに書き換える（`nightStyle.ts`）。手紙の円は GeoJSON のレイヤーで描く。
- **理由**：API キーが要らず、審査員の環境でもそのまま動く。
- **ほかの案**：Leaflet + 暗色タイル。うまくいかなかったときの控えとして仕様に残してある。

### 18. 位置の取得元を gps / manual で切り替える（デモモード）

- **決めたこと**：位置を配る部品（`LocationProvider`）を 1 つにし、地図をタップした場所を現在地にできる。初期値は東京駅。
- **理由**：審査員はその場所まで歩けない。判定のコードは GPS のときと同じものが動くので、デモ用の別の道を作らずに済む。
- **ほかの案**：デモ用に「どこでも開けられる」抜け道を作る。本物の判定を見せられなくなる。

### 19. 開封済みの記録は端末にだけ持つ

- **決めたこと**：封を切った手紙の ID を IndexedDB に置く。サーバーには送らない。
- **理由**：「いつ、どこで開けたか」という行動の記録を運営に渡さない。
- **正直に書くこと**：別の端末では未開封に見える（そもそも鍵がないので開けられない）。

## 三日目 本格的な動作を導入（2026-11-12）

### 20. 「ようこそ」の手紙も、本物の暗号化で作る

- **決めたこと**：初回に、自分あての手紙をふつうの手紙と同じ手順で封をして埋める。差出人の表示だけ「アルクカナ」。
- **理由**：審査員が起動直後に「掘る → 封を切る → しくみを見る」を、作りものではないデータで体験できる。
- **ほかの案**：画面にだけ出す見本の手紙。「運営から見えるもの」に出すデータがなくなる。

### 21. 「運営から見えるもの」は、同じ手紙の 2 つの姿を並べる

- **決めたこと**：Firestore にある生の値（項目ごとに「読める／読めない」）と、端末で開いた結果を、タブで切り替える。入口は手紙の下の小さなリンクだけ。
- **理由**：「運営にも読めない」を、説明ではなく実物で見せる。ふだん使う人の導線には出さない。

### 22. 共有リンクに入れるのは uid だけ。合言葉で確かめる

- **決めたこと**：リンクは `/friends?add={uid}`。開いた側が公開鍵をサーバーから読み、合言葉 4 語を表示して、追加するかを決める。
- **理由**：リンクが短く、QR も粗くて読みやすい。サーバーが別の鍵を返しても、2 人が合言葉を見比べれば気づける。
- **ほかの案**：公開鍵そのものをリンクに入れる。長くなり、QR が細かくなる。

### 23. 追加したときの公開鍵を使いつづける

- **決めたこと**：友だちの公開鍵は端末に保存し、封をするときはその鍵を使う。送るたびにサーバーから読みなおさない。
- **理由**：合言葉で確かめた鍵で必ず封をするため。あとからサーバーの鍵がすり替わっても影響を受けない。
- **正直に書くこと**：相手が鍵を作りなおしたら、もう一度追加してもらう必要がある。

### 24. 友だちの一覧はサーバーに置かない

- **決めたこと**：一覧と呼び名は IndexedDB にだけ置く。
- **理由**：だれとつながっているかを運営に知らせない。
- **正直に書くこと**：手紙の `to` と `from` は平文なので、手紙を送った相手は運営にわかる。

### 25. 返事のあて先と場所は URL に入れない

- **決めたこと**：「ここに返事を埋める」は、react-router の `state` であて先と座標を渡す。
- **理由**：座標を URL や履歴に残さない。

### 26. QR は表示だけ。読み取りはスマホ標準のカメラ

- **決めたこと**：`qrcode` で共有リンクを QR にする。アプリ内のスキャナは作らない。
- **理由**：カメラの許可を取る画面が要らず、作るものが少ない。

### 27. 封蝋は、復号に成功してから割る

- **決めたこと**：「封を切る」で先に復号し、成功したら封蝋を割り、演出が終わってから紙面を出す。`motion` を使うのはここだけ。「視差効果を減らす」設定では演出を飛ばす。
- **理由**：先に割ると、失敗したときに封蝋だけ割れた状態になる。

### 28. PWA は「ホーム画面に追加できる」まで

- **決めたこと**：端末に置くのはアプリ本体とアイコンだけ。新しい版は次に開いたときに自動で入れ替える。
- **理由**：地図と手紙は通信が要るので、オフラインで全部動かすことは目指さない。
- **正直に書くこと**：JS が 1 本で約 2.1MB あるので、端末に置く上限を 3MB に上げた。

### 29. 想定外のエラーは、いちばん外側で受け止める

- **決めたこと**：`ErrorBoundary` で画面全体を包み、「読み込みなおす」を出す。
- **理由**：審査員の手元で真っ白になると、何も見てもらえない。
- **補足**：描画エラーを受け止める仕組みは React ではクラスでしか書けないので、ここだけクラス。

## 四日目 仕上げ（2026-11-13）

### 30. ルールは、本番に「拒否されるはずの操作」を送って確かめた

- **決めたこと**：Firebase Emulator の代わりに、開発用ブラウザから本番のルールに対して 17 件の操作を送り、すべて拒否されることを確かめた（通るはずの操作が通ることも確認）。
- **理由**：手元の Mac に Java がなく、Emulator を動かせなかった。
- **試した内容**：手紙の書き換え、他人の手紙の一覧・ID 指定の読み取り・削除、差出人のなりすまし、存在しない相手あて、余計な項目、16KB 超え、日時の指定、IV の長さ違い、第三者ぶんの鍵、他人の `users` への書き込み、`users` への余計な項目・`createdAt` の書き換え・形のおかしい公開鍵。
- **正直に書くこと**：自動テストにはなっていない。ルールを変えたら、もう一度手で送る必要がある。

### 31. iPhone のホーム画面向けの指定を足した

- **決めたこと**：`apple-mobile-web-app-capable` などの Apple 独自の `<meta>` と、viewport の `viewport-fit=cover` を足した。
- **理由**：iPhone はマニフェストだけではアドレスバーが消えなかった。`viewport-fit=cover` が無いと、画面下の横棒のぶんの余白（`env(safe-area-inset-bottom)`）が常に 0 になり、タブバーと重なった。

### 32. タブのアイコンは SVG を直接書く

- **決めたこと**：4 つだけなので、アイコン用のライブラリは入れず、`TabBar.tsx` に SVG を書く。色は `currentColor`。
- **理由**：依存を増やさない。開いているタブの色が文字と一緒に変わる。
